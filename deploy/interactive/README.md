# Same-host deployment operations

The production stack is `dml-interactive`: management, userspace tailscale,
restricted one-off bootstrap, gateway and explicit one-off migrate. Installed
Headscale remains external. Nothing in Compose/restart starts, resets or restarts
its systemd daemon. ARM64 and AMD64 are supported by the pinned public images.
CPU/memory bounds and rotating logs keep gateway traffic bounded on this host.

## Provision before enabling the push hook

1. Validate CI, shell checks, disposable restart and real network E2E first.
2. Locate the actual Linux push hook and its checkout. The repository Actions
   deploy job targets an external macOS script, which is not evidence that it
   updates this host. No Linux hook has yet been identified in inspected systemd,
   cron, user configuration or repository Git hook paths.
3. Back up and migrate existing Scheduler Postgres storage deliberately with
   `POSTGRES_BACKUP_DIR=<protected-absolute-directory> bash deploy/migrate-postgres-storage.sh`.
   This separate one-time operation stops API/DB, takes a SQL backup and copies
   offline data to external `scheduler-postgres-data`. It preserves the original
   volume. Set matching `POSTGRES_DATA_VOLUME` in Scheduler deployment environment
   if another stable name is used. Do not attach an empty volume as a migration.
   Ordinary `restart.sh` fails before builds on missing/mismatched storage and
   uses `--no-recreate` for db/redis.
4. Create explicitly managed private `dml-control` network. Management has no
   published ports. Future Scheduler can attach to this stable network; no
   `scheduler_default` lifecycle dependency is introduced.
5. Provision stable files once with the offline `provision_secrets.py` helper,
   using an isolated environment with management requirements. Protect host
   directory/files with mode 0750/0640 and service group 10001. Independently
   provision a Headscale administrative API key into the `headscale` file without
   printing it. Management alone mounts that file, controller secret, encryption
   and private signing key. Gateway mounts only gateway secret/public keys;
   bootstrap adds only its restricted secret. Never bake runtime keys into images.
6. Protect `/etc/distributed-ml/interactive.env` and fill values from
   `interactive.env.example`. Stable volumes have explicit names for management,
   sidecar state/socket and bootstrap metadata. Credentials/identity are never
   regenerated by pushes. Use trusted HTTPS and exact browser Origins including
   nonstandard ports.
7. Provision Headscale tag owners and the required gateway-to-endpoint TCP 9000
   grant separately, preserving unrelated existing policy. Management reads
   policy through the pinned API and fails readiness for absent/broad interactive
   rules; it never writes policy. Existing permissive/default policy is not a
   valid interactive-role boundary. Do not reset or bulk-delete existing nodes.
8. Prove the administrative HTTPS API is reachable with valid TLS from management
   bridge networking. The installed config advertises `https://headscale.zulfiker.xyz`
   and listens only on host loopback; this observation alone does not prove
   administrative proxy reachability. `host.docker.internal` cannot expose a
   127.0.0.1-only listener. Prefer a restricted existing HTTPS proxy or separately
   provision a narrow private host proxy. Never broaden admin exposure globally.
9. Merge the gateway location into the existing trusted HTTPS proxy. Mapping is
   on tailscale's shared namespace at `127.0.0.1:8030`, never on gateway itself.
   SOCKS and LocalAPI have no published port. The supplied nginx example shows
   upgrades/timeouts. For Caddy, place `handle /v1/connect/* { reverse_proxy
   127.0.0.1:8030 }` before the existing Scheduler fallback. Preserve its virtual
   host/certificate settings. Verify actual WSS with an issued ticket; container
   health alone is not public ingress evidence.
10. Set `REQUIRE_INTERACTIVE=1` in the real push-hook environment, then invoke
    `restart.sh` from the validated checkout. If config/manifest/health fails,
    enabled services must fail visibly; no feature-disable fallback is available.

## Restart and failure semantics

`restart.sh` resolves paths from itself, serializes the entire update with flock,
validates config/storage/network, builds all app images before stopping anything,
keeps Scheduler db/redis containers/storage, recreates API and checks HTTP, stops
interactive writers, migrates with SQLite-consistent private backup, recreates
management and checks admin/policy readiness, retains or updates sidecar, runs
idempotent bootstrap and recreates gateway against the current namespace.
Migration/bootstrap/readiness failures remain nonzero and report partial update
with safe status metadata. No network-filter stop, image removal, global cleanup,
`down -v`, volume pruning or host Headscale restart is used.

Push updates interrupt active streams. SIGTERM has a bounded grace window and
attempts session release; clients request new tickets before reconnecting. The
script is not atomic rollback or zero downtime. Failure after Scheduler changes
can leave a partial deployment; preserve state and diagnose rather than reset.
`RESTART_WAIT_TIMEOUT` defaults to 120s; `INTERACTIVE_ENV_FILE` can select another
protected host file. Build/migrate one-off image names are shared explicitly.

Management supports one process/reconciler and versioned SQLite migrations only.
Protect the `.pre-migration` backup alongside the DB; never upload it, private
keys, env files, raw Docker inspection or key listings. Future nontrivial schema
migrations must be sequential and backward/forward compatible. Restore is an
explicit maintenance operation after inspecting schema/application compatibility,
not an automatic reset/rollback path.

## Rotation and decommission

Rotate signing keys with bounded public-key overlap as described in management
README, retaining durable DB and current encryption/service identity across pushes.
Changing the Fernet key without handling pending ciphertext loses idempotent key
replay; expire/revoke pending enrollments before a deliberate replacement.

Controller decommissions resources with DELETE `/internal/v1/resources/{id}` and
polls its enrollment status until REVOKED. Admission is denied before remote
cleanup. To decommission gateway, controller revokes its exact enrollment, then
operator stops gateway and logs sidecar out through private LocalAPI. Explicitly
reset only its bootstrap metadata after cleanup, choose a new gateway generation
and rerun helper. Ordinary restart is never decommissioning or a reason to mint
another key. Unmanaged state/revoked identity fails for explicit recovery.

## Troubleshooting and verification

Read `/health/live` for process-only liveness; `/health/ready` for real dependencies.
503 management: check schema migration, protected file permissions, verified
admin HTTPS and installed explicit policy. 503 gateway: check own enrollment,
sidecar Running/socket/SOCKS and management readiness. REGISTERED/OFFLINE endpoint:
check controller lease, node online/fresh observation and exact gateway TCP probe.
409 means conflicting idempotency/stale generation/version; do not bypass fencing.
UNKNOWN_RESULT means remote creation may have succeeded: wait for its bounded TTL
and explicitly replace; do not adopt keys/nodes by hostname/timestamps.

Portable CI validates disposable APIs/real TCP and restart ordering, not this
host's WSS/admin exposure or arbitrary cross-machine NAT. Production enablement
requires the operational checks above. No production cutover has been claimed
without those gates.
