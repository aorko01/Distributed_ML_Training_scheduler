# Durable interactive workspaces and batch training from the saved image

Status: implementation in the current worktree as of 2026-09-25. VS Code Remote-SSH remains the established working path. Sections 2 and 4 record the baseline gaps and implementation instructions from before these changes; the status below records what has since been implemented and verified. Deployment flags remain off pending the real multi-host acceptance gate.

### Implementation status

- Scheduler now dispatches fenced Save operations, starts an automatic Save and Stop before a runtime deadline, verifies private artifact receipts, publishes immutable SNAPSHOT revisions with saved-head CAS, and reconciles live or direct training submissions into digest-pinned Jobs.
- Worker commits the exact workload through Docker, excludes per-runtime SSH files with a tmpfs, exports a bounded disk-backed archive, uploads with an operation capability, and retains local staging until Scheduler accepts the receipt. Browser writes drain for commit; existing VS Code sessions remain attached to the running workload.
- Object Store has a private `snapshots` bucket and scoped, authenticated streaming transport. Builder validates the archive/image, preserves the verified SSH profile, pushes a unique revision tag, and resolves and checks a registry digest. Batch Worker runs the selected digest and preserves the saved image's user/Python environment.
- UI flushes browser buffers, accepts training settings, shows saved revision history, supports Save for Later/Save and Stop/direct training, and resumes Save/Submission polling after refresh. The operations runbook is `docs/workspace-snapshot-operations.md`.
- Local checks passed: Scheduler, Worker, and Builder unit suites; Object Store transport tests; TypeScript check, UI tests, and Node 22 production build; a disposable PostgreSQL migration run; Docker commit/save/load and batch command smokes. These checks do **not** establish registry/MinIO/GPU behavior across hosts or continued VS Code connection through a real Save.
- Required before enabling flags: the disposable two-Worker acceptance and failure-injection gate in §6, including a real SSH save/reopen and completed GPU training Job. The Scheduler and Object Store hosts also need the same dedicated snapshot service key mounted as documented.

## 1. Product contract and definition of done

A user creates an interactive workspace, opens its browser editor/terminal or the existing VS Code Remote-SSH connection, changes a file under `/workspace`, installs a Python package with `pip`, optionally installs an OS package with `sudo apt-get`, and runs the code. A durable save uses Docker commit on the **workload container**, capturing its writable filesystem, including `/workspace`, `/opt/dml-venv`, `/home/dml`, and OS package changes. It publishes an immutable, digest-addressed image through the trusted Builder. After the original container is removed, a new runtime can start from that saved revision and demonstrate the same file, Python import, OS executable, and VS Code Remote-SSH capability. The user can submit that exact saved revision to the existing VRAM-estimation and batch-training pipeline; batch execution uses the same published image digest and the user's selected command.

The UI must make the two meanings of “save” clear: editor Save All writes browser buffers to the *live container*; VS Code file Save also writes only to the live container; Save for Later waits for a durable revision. A successful durable save means the image is in the registry, the Scheduler recorded its digest, and a fresh Worker can pull it. A request being accepted, an archive existing on one Worker, or a tag alone is not success. Stop initiated by the user must offer/perform **Save and Stop** as the normal path; if saving fails, keep the runtime and its SSH connection available when possible and show the failure. The user may explicitly discard changes. A scheduled lifetime stop should start a save with lead time and not remove the workload until success/failure is recorded; coordinate both Worker limits (600 seconds for ordinary runtimes, configured SSH limit for SSH-ready runtimes) with this grace period or the container may be killed mid-save. For an abrupt Worker/host loss, only the last successfully published revision can be guaranteed; periodic checkpointing can reduce that window, but snapshots alone cannot guarantee every unsaved byte through a sudden host failure. State this limitation honestly in the UI and operations docs.

Acceptance demonstration on a real Docker-enabled deployment:

1. Build a new SSH-capable developer-profile workspace, start it, connect with VS Code Remote-SSH, create `/workspace/train.py` with a unique marker, run `pip install six` and `sudo apt-get install -y ffmpeg` in its terminal, and execute the script in the same runtime. Confirm browser and VS Code edits are mutually visible.
2. Save and wait for `SUCCEEDED`; verify an `IMAGE_READY` SNAPSHOT revision with a canonical `repository@sha256:...` reference, and verify the digest can be pulled on another Worker/host.
3. Confirm Save for Later leaves the existing VS Code session usable. Stop/remove the original workload, start a new runtime from that saved revision, reconnect VS Code using the new runtime/generation, and verify the marker, `import six`, and `ffmpeg -version` without reinstalling anything. The new runtime gets a fresh SSH host key; the old host/grants remain revoked.
4. Submit that revision with `python train.py`; verify the resulting Job enters VRAM estimation, then normal batch training, pulls the **same digest**, runs the saved code with the installed packages, and reports logs/results in the existing Job UI.
5. Exercise failures and retries: a lost Worker lease, duplicate Save/Submit requests, upload interruption, Builder restart after push, registry failure, obsolete snapshot callback, and publication out of order must not report success or move the workspace back to an older revision.

## 3. Chosen architecture and invariants

Use the current separation of responsibilities:

```text
Browser --owner API--> Scheduler Save/Submission row
Scheduler --fenced decision in heartbeat--> authoritative Worker
Worker --commit exact workload--> private immutable artifact in object store
Worker --fenced receipt--> Scheduler creates one SNAPSHOT revision
Builder --claim/verify/load/push--> registry digest --ready callback--> Scheduler
Scheduler --atomic publication--> saved head / Save SUCCEEDED
Scheduler --training coordinator--> Job referencing the saved digest
Batch Worker --pull by digest--> VRAM estimate --> training
```

Invariants to implement and test:

- A Save is tied to owner, workspace, runtime generation, parent revision, assignment ID, attempt token, and current Worker. No browser receives a Docker identifier, object-store secret, upload capability, or builder credential.
- The image is immutable after publication. A tag names one revision/build attempt; pulls and Job payloads use `repository@sha256:...`. Do not rewrite `latest` or mutate an `IMAGE_READY` revision.
- Durable head publication is compare-and-swap (CAS): pin `expected_saved_revision_id` when each Save is created and advance the head only if it still equals that value. A late older build becomes a historical ready revision without replacing a newer head. Retain it, mark the Save `SUCCEEDED`, leave `saved_revision_id` unchanged, and return `head_advanced=false`; the user can select that historical revision explicitly.
- A snapshot must contain the files and packages users actually used. `/workspace`, `/opt/dml-venv`, `/home/dml`, apt's installed files, and the selected command environment must be in the image's writable layer. Reject any workload image that declares Docker volumes on relevant paths or has runtime mounts covering those paths. Document that external data, mounts, GPU drivers, runtime process state, and in-memory variables are not part of a saved image.
- Preserve the SSH-capable image profile and its trusted Builder metadata through snapshot import so reopening a saved revision remains VS Code-capable. Per-runtime SSH host keys, authorized client keys, tickets, grants, and connection state must not be committed or reused. Put runtime SSH files under a verified ephemeral mount excluded by Docker commit, or otherwise prove they are absent from the committed image without disrupting the live session. A reopened runtime initializes fresh SSH state under its own generation.
- Never mark Save/Submission success from the browser request alone. Never create a batch Job until the Save's image digest is accepted and the source runtime is stopped/released (or an explicit, safely tested concurrent policy exists). Existing resource admission is exclusive for interactive work.
- Retry an operation under its original idempotency/fencing identity. Reconcile after process crashes. Only remove exact operation-owned temporary images/files/objects after confirming publication or terminal failure; never daemon-wide prune or wildcard delete.

### 4.1 Align schema, migrations, and public API

Compare SQL constraints with ORM definitions; `create_all()` is not a migration for existing PostgreSQL. Add an FK for `saved_revision_id` to a revision in the same workspace if compatible with the migration strategy. Validate on an existing database as well as a new one.

Make public workspace detail return `saved_revision_id`, a usable saved revision summary, and a separately labeled pending/latest revision. Save status should include target revision, published digest, `head_advanced`, and safe failure code once terminal. Submission status should include the eventual Job ID and a linkable status. ### 4.2 Dispatch Save requests to the live Worker

Extend Scheduler worker heartbeat/decision logic in `Scheduler/app/services/scheduling/claims.py` and its strict schemas. Return a bounded `capture_save` command containing operation ID, workspace ID, runtime/assignment/generation fence, parent revision, purpose, and deadline, but no object credentials. Lock in the same Worker → assignment → runtime order as existing claims. Only dispatch when the runtime is `READY`, desired state `RUNNING`, the exact assignment is active, and the Save is `REQUESTED`; transition to `CAPTURING` under the same transaction. Duplicate heartbeats may repeat the same operation ID, and a newer generation must never receive an older command.

Extend `Worker/managed_worker.py` and `Worker/interactive/manager.py` to accept that command while their heartbeat and runtime health loops continue. Gate browser editor writes and PTY commands, drain in-flight browser file writes, and take a bounded point-in-time Docker commit. VS Code terminal and SFTP writes bypass that browser gate: temporarily deny new SSH opens during the commit, give the user a save-in-progress notice, and wait or fail with a clear retry message if a known package install or transfer is still active. Docker's pause provides the final filesystem snapshot boundary; document that a user must save VS Code buffers and finish commands before requesting a revision, because a running multi-file operation cannot be made application-atomic by Docker commit. Existing VS Code channels may briefly stall, then must resume with the same runtime, grant policy, and host key after Save for Later succeeds or fails. Do **not** leave the workload paused during a potentially multi-gigabyte export/upload. Verify authority before every Docker side effect and throughout long streaming work. Persist operation ID, artifact path/hash, and progress in the Worker journal for restart reconciliation. A repeated dispatch resumes or returns the existing result; it never creates a second unrelated snapshot.

Harden `Worker/interactive/snapshot.py`: verify all workload labels (worker, runtime, workspace, revision, assignment/generation), image config and lack of mounts/volumes over saved paths, and use the Docker SDK's actual commit/pause API correctly. Verify that `/run/dml-vscode-ssh` or its configured successor is ephemeral and excluded from the commit; inspect a loaded test snapshot to prove host private keys, authorized keys, and runtime SSH configuration are absent. Commit to an operation-scoped image/tag; export it to a bounded, disk-backed stream, compute SHA-256 and byte count as it writes, enforce maximum size and elapsed time, and keep adequate quota/headroom. Correct image cleanup through `images.remove()` by exact staging tag/ID; `remove_exact()` is container-only. On cancellation or failure, unpause and release any gate. Do not remove the artifact or image before durable receipt is acknowledged. Handle Worker restart/lease loss without silently claiming success.

### 4.3 Build a real private artifact transport

Replace the placeholder in `Scheduler/app/services/snapshot_artifact_service.py` with a narrow, fenced transport contract. Preferred implementation: Scheduler issues a short-lived, single-object, single-operation presigned multipart upload through MinIO/S3 for the exact `snapshots/<workspace>/<parent>/<operation>/<sha>.tar.gz` key, or a trusted upload service that streams bytes and authenticates Worker identity. Because SHA is only known after export, use a server-owned temporary operation key then atomically record its immutable object version/hash, or complete export first and request the final-key capability; make the key/receipt deterministic on retries. Never send root MinIO credentials to the Worker/browser. Separate snapshot storage authorization from the generic `Object_store/main.py` endpoints; enforce bucket/key prefix, size, expiry, content hash, and no overwrite (version ID or conditional put). Do not send an 8 GiB file through FastAPI `UploadFile.read()`.

On Worker completion, Scheduler must **head/stat** the exact object/version using trusted storage credentials, confirm nonzero size within limit, and verify SHA-256 (stream server-side if the object store cannot attest the checksum). Only then transactionally create one `workspace_snapshot_artifacts` row and one `SNAPSHOT` revision, set Save to `PUBLISH_QUEUED`, and return the same target revision for an identical retry. Reject conflicting receipt data and stale assignment/generation. Require Builder authentication for a time-limited download descriptor scoped to that specific accepted artifact; Builder must fetch through a credentialed/signed URL or trusted internal stream. Do not trust a bare browser-supplied key or the current generic unauthenticated GET. Add cleanup/reconciliation for abandoned multipart uploads and exact old artifacts after retention review.

### 4.4 Verify, import, and publish on the Builder

Continue to use `Docker_Image_Builder/builder.py`'s interactive claim/heartbeat and `interactive_build.py`'s `SNAPSHOT` branch. Claim the operation's descriptor; stream and verify the compressed artifact without accumulating it in an 8 GiB `bytearray`. Use a disk-backed bounded spool and Docker load stream/file API. Check byte count, SHA-256, archive structure/loaded-image count, image ID, architecture/OS, `User=10001:10001`, `WorkingDir=/workspace`, no volumes, developer profile label, expected source lineage, and no unexpected entrypoint/environment secret. Set bounded Docker pull/load/push timeouts and cancel on lease loss. Treat mismatched or corrupt user artifact as a stable Save failure and transient store/registry trouble as retryable infrastructure failure.

Tag the **verified loaded image ID** with the unique revision-and-attempt tag, push with Builder-only registry credentials, retrieve registry manifest digest, and verify a fresh pull by digest before notifying Scheduler `ready`. Validate the loaded image's `io.dml.vscode-ssh-profile=v1` label and required SSH binaries/wrapper when claiming SSH capability; return `ssh_profile='v1'` in the SNAPSHOT Builder result and carry it through the ready callback to the revision. Preserve the existing SSH startup eligibility rule; do not infer capability from an arbitrary user label alone. Keep the Builder's local artifact ledger for a crash after push/before callback. If a derived training image is ever built, push its returned child image ID, not `loaded_id`; fix `import_snapshot(...training_command=...)` and its tests. The simpler first integration is to use the immutable saved image directly and store command on the Job, since the current batch executor already supplies the command at runtime. Do not make a second build a prerequisite for submission unless batch behavior requires it.

`mark_ready()` must atomically transition the matching Save to `SUCCEEDED`, record accepted digest, apply the head CAS, and advance any waiting training submission. A callback with the same digest is idempotent; a conflicting digest or stale build attempt is rejected. Make `PUBLISHING` visible while Builder owns the revision. A terminal Builder failure must set both revision and Save terminal states and propagate a safe code to the UI. The existing migration's immutable-ready trigger prohibits a second update of a ready row; write all immutable fields/profile in the first ready transaction and remove the current later profile backfill behavior.

### 4.5 Reopen the saved image and keep the history correct

`Scheduler/app/services/interactive_runtime_service.py:start()` already prefers `saved_revision_id` when no revision is specified. Ensure it selects the published head, never a queued/latest revision, and accepts an explicit owned `IMAGE_READY` historical revision. Return the chosen digest and revision identity in the runtime record; Worker must pull and validate that digest as it does now. The new runtime is a new generation and has its own writable layer and newly initialized SSH host key/grants; `dml-ssh configure` must target its new host/generation while the previous one remains revoked. Saving it creates another immutable SNAPSHOT child; do not mutate the previous image. For repeated saves from the same live runtime, keep `Save.parent_revision_id` as the runtime's original image (the API fence) and pin `expected_saved_revision_id` from the workspace when each Save starts. Each save captures the entire current filesystem; the second save can therefore advance the head after the first without rebasing the running container. Give each snapshot revision a `source_runtime_revision_id` and set its lineage `parent_revision_id` to the head expected by that Save. On publication, CAS against the pinned expected head. A save from a historical runtime may publish a branch without moving the head if another branch has already advanced it. Every intentional save needs a new idempotency key.

Extend `WorkspaceTrainingSubmission` with nullable runtime/save fields for this direct path and a unique owner/workspace/revision/request-key identity. Set its status directly to `VRAM_ESTIMATION_PENDING`; the saved image already exists, so do not enqueue the ordinary image Builder. Never derive batch input from mutable workspace head after the submission was created. A retry returns the same submission and Job IDs.

Map and validate the new Job fields in `job_model.py`, `job_service.py`, `_format_job_response()`, Scheduler claim payloads, and Worker executor. For `WORKSPACE_REVISION`, refuse empty/fallback `latest`, pull by digest, and verify the image identity before starting estimation/training/retry. Keep current archive/package-only behavior intact. Revisit the batch executor's `_container_user_args()` and `_prepare_output_mount()`: it overrides the image user and `HOME`, and bind-mounts a copied `/workspace` for outputs. Verify the copied source is executable by the batch UID, that the saved `/opt/dml-venv` PATH/Python remains active, that installed apt binaries are present, and that checkpoint/output collection still works. Resolve permissions explicitly rather than silently running a different environment. The existing `command` can remain a validated simple Python invocation; use `shlex.split` once into argv and avoid shell evaluation. ## 5. State transitions, failure policy, and reconciliation

Maintain one transactionally consistent state machine. A suggested mapping:

| Event | Save | Revision | Submission | Required result |
| --- | --- | --- | --- | --- |
| Owner request accepted | `REQUESTED` | none | `SAVING` for Submit | Return operation IDs only. |
| Worker accepts fence | `CAPTURING` | none | unchanged | Gate writes; exact workload commit. |
| Artifact streaming/receipt | `UPLOADING` | none | unchanged | Verify private object/version/hash; retry same operation. |
| Receipt accepted | `PUBLISH_QUEUED` | `QUEUED` SNAPSHOT | `WAITING_FOR_REVISION` | Exactly one target revision. |
| Builder owns revision | `PUBLISHING` | `BUILDING` | unchanged | Fenced Builder lease. |
| Digest accepted | `SUCCEEDED` | `IMAGE_READY` | `STOPPING_RUNTIME` for Submit | CAS saved head; no stale overwrite. |
| Runtime released | unchanged | unchanged | `PREPARING_JOB` | Create one digest-pinned Job. |
| Job committed | unchanged | unchanged | `JOB_CREATED` | Job enters VRAM-estimation queue. |
| Terminal capture/import/registry error | `FAILED` or retryable active state | `FAILED` only when terminal | `FAILED` for Submit | Stable public code; old saved head remains usable. |

Run a Scheduler reconciler on startup and periodically: find aged nonterminal Save/Submission rows, inspect authoritative assignment/artifact/revision/Builder lease state, resume idempotently or mark terminal with a specific reason. The Worker restart path currently cleans up assignments; for a completed local export, it must first reconcile whether the artifact was accepted and avoid destroying the only copy. If the Worker or host is permanently gone before upload, fail that Save and retain the previous saved head. A timeout/stop should not race the save: define a grace period and prevent runtime cleanup until a requested capture reaches durable object receipt or fails. Apply this to the ordinary and SSH-ready lifetime limits; new SSH grants should stop once Save and Stop begins, and active connections should close only after successful publication or explicit discard. Registry failure must leave the previous saved head intact and retry publication under a fenced attempt. Log operation/revision/assignment IDs and safe stage names without printing package output, object capabilities, or secrets.
